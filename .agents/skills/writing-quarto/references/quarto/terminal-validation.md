# 终端命令与实测输出

本文件是命令、说明与输出展示细则的唯一出处，其他文件只保留指针，不重复展开。

## 命令与结果的顺序

命令块前分别说明执行环境和前置条件，不把权限、系统版本、命令和结果挤在同一句中。需要读者根据输出判断工具是否可用时，命令后使用独立的 `text` 块展示典型输出，并说明输出顺序、可变化部分和成功判据。推荐使用以下顺序：

1. 说明先决条件和执行位置。
2. 给出可复制的命令。
3. 展示预期结果或真实输出。
4. 说明成功判据、证据边界和下一步。

有明确先后关系的动作使用有序列表，并列的系统要求、工具要求和注意事项使用无序列表。每个代码块前用一句正文说明目的，块后只写继续操作所需的判据或下一步。

后续命令依赖前一条命令的输出时，正文必须说明从输出中复制什么、如何用它完成占位符替换，以及什么时候执行下一条命令。不能只写「记下名称后再安装」，否则新手需要自行判断取值对象和替换位置。

恢复后的可观察状态本身需要拆解说明，并且其后没有必经动作时，可以用结果型 Callout 承接精确判据和说明列表。正文仍要先保留检查动作。结果型 Callout 的边界见知识库 `bg-section-focus-density-v1`。

## 代码块前的标点

代码块前不固定使用冒号，按引导句与块内容的关系选择：

| 引导句职责 | 末尾 | 示例 |
|---|---|---|
| 完整动作或条件，命令是下一步执行 | `。` | 在 WSL Ubuntu 中执行下面的命令配置工程。 |
| 用「如下、以下、例如」直接引出代码或输出 | `：` | 配置输出如下： |
| 普通过渡，块只是接下来展示的内容 | `。` | 接下来查看阶段目录。 |

只有引导句明确把代码或输出作为「如下」等词语的内容时才使用全角冒号。正文不以逗号、半角 `:` 或 `：。` 结束，行内代码和代码块内部照抄真实语法。

## 实测输出

目录、文件名、版本号、工具状态和终端输出应先通过磁盘或命令获取，再写入文档。标记为在 WSL Ubuntu 中运行的只读验证命令，先实际执行，再保留能判断成功的关键行。输出过长时可以筛选版本行、状态行或关键错误，但不能凭空编写结果。环境不可用时只写检查方法，并明确没有实测输出。

## 命令、说明与输出三分法

命令块只放能直接复制执行的命令，以及紧贴在命令上方的原生注释。不加 `$ ` 或 `PS>` 提示符，不在命令行末尾追加注释。每个代码块在首条命令上方写一条总注释，说明整块要做什么。只有单个依赖或用途不明显、容易误用时，才在该命令上方补一行子注释。输出放在紧随其后的 `text` 块中，命令块与输出块之间只留一个空行。

代码块注释一行只承担一个职责。总注释和子注释都用短句，不用中文冒号或分号串联多个动作。片段内注释硬限（每处 ≤2 行、单行 ≤40 字）见知识库 `bg-qmd-element-cases-v1`。代码块中不使用 Markdown 强调符号。

标点规则只作用于正文、标题、表格和列表，行内代码与代码块内部照抄真实语法。把多条命令串进一句话，读者无法判断该复制哪一行，应当拆成独立的代码块或独立句子。留在同一块内的多条命令职责不同时，逐条写子注释说明各自用途；读者只需执行其中一条时，拆成独立代码块，并在正文写明先执行哪条、什么情况下改用另一条。多命令块后的逐条讲解用无序列表（格式见知识库 `bg-paragraph-list-style-v1`）。

按执行环境选择代码块语言和标题：

| 内容 | 属性围栏 | 约定 |
|---|---|---|
| WSL、Ubuntu 和 Shell 脚本 | `{.bash filename="WSL Ubuntu（仓库根目录）"}` | 脚本文件用真实文件名。`#` 注释单独成行，写在被说明命令的正上方 |
| 真实输出、目录树 | `{.text filename="输出"}` | 目录树标题写 `阶段目录` 一类场景名。不放命令、`$ ` 或 `PS>` |

命令有输出需要展示时，说明成功判据的正文写在两个块之间，输出进独立的 `text` 块。典型路径、版本号和其他环境相关值可能变化时，明确哪些内容只作示例，以及应观察的稳定形态。结论不得超过命令实际观察到的事实：`command -v` 只能证明 Shell 能定位命令，版本查询只能证明命令可以启动；编译、运行、测试是否可用，必须由对应任务的实际操作验证。命令正常结束本身就是隐含结果时，不追加通用成功句。

## 成功判据三件套

输出不稳定或篇幅过长的命令，不展示完整输出，改给可核对的判据。三条按可得性写，不必凑齐：

| 判据 | 写法 | 适用 |
|---|---|---|
| 退出码 | “退出码为 0” | 任何被脚本或后续步骤依赖的命令 |
| 关键行 | “输出包含 `Build files have been written to`” | 交互式执行，读者用眼睛确认 |
| 产物文件 | “`build/bin/tic_tac_toe_cli` 存在” | 构建、生成配置、导出数据 |

配置与构建这类分阶段的命令，两条阶段各自给一条判据，再补一句「两阶段都成功才算流程完成」。判据写在命令块之后，不重复正文已说明的用途。

## 破坏性命令四要素

删除、清空、覆盖类命令进入正文时，必须同时交代四件事，缺一项就不要给出该命令：

1. 删什么：具体路径与其内容性质。
2. 不删什么：读者真正担心丢失的东西，例如源码与构建配置。
3. 如何恢复：能否重新生成，或恢复需要哪些前置。
4. 替代方案：先给出可逆写法，把不可逆写法放在确认新状态正常之后。

`rm -rf` 只有在没有安全替代、且恢复路径明确时才写，并放在 warning callout 或独立段落里，不与成功路径混排。删除 `build/` 属于可重建产物，恢复方式是重跑配置。

## 常见错误使用三步诊断流

常见错误放在本章回顾之前，`## 常见错误` 负责导航。每个故障用一个描述现象的 `###`，标题后的第一句同时说明触发条件与可观察现象，下面只保留「定位 → 修复 → 验证」三个有序步骤。

定位步骤只放收敛问题所需的最小检查，先确认执行位置与前置状态，再检查故障本身。确认执行位置用一条可观察的判据，例如用 `pwd` 确认当前目录以阶段目录结尾，或用 `ls CMakeLists.txt` 确认当前位于工程根目录。修复步骤必须复用定位得到的具体对象，并提供回到成功路径的动作。验证步骤给出一个可观察结果。修复动作必须与定位得到的故障对象一致：清理目标产物不能替代清除 CMake 配置缓存，排查缓存或工具链问题时也不顺带更换构建类型。

故障标题后的首句直接回答发生了什么或先检查什么。步骤名写成加粗的 `1. **定位失败来源**`，说明文字另起缩进段；只加粗步骤名，说明、命令和参数保持常规字重。一个步骤中存在多个可选原因时，在该步骤下使用无序列表。三步中如果两步使用代码块，第三步包含可复制命令时也必须使用代码块。

正文默认沿正确流程书写，不把「出现 warning/error 后怎么办」夹在成功路径中。需要保留的问题说明放入 `## 常见错误`，每个症状使用 `###`。中间实现章的常见错误承接开发流程的报错记录，口径见知识库 `bg-engineering-storyline-v1`。
