# 中文技术文档写作原则

本文件是所有中文内容的最高优先 how 规则。规则冲突时，以读者能否完成当前任务为准。本仓的语气语域判定（`bg-chinese-voice-register-v1`）、术语与禁用词（`bg-terminology-v1`）、段落与列表细则（`bg-paragraph-list-style-v1`）保留在知识库，本文件只写可执行的通用做法，与知识文件冲突时以知识文件为准。

## 先让新人完成任务

- 开篇说明读者在做什么、完成后能得到什么，不先铺陈历史、架构和完整背景。
- 每页只保留一条成功路径。高级选项、边缘情况和内部实现后置，不能阻塞第一次成功。
- 保留标准术语，但首次出现时用一句白话解释；术语卡用就近的 callout 承载（写法见 `authoring.md`）。缩写先写全称。
- 不假设读者知道工具名、命令参数、目录布局或错误输出代表的含义。

## 句子要短，术语要稳

- 一句话只推进一个动作或结论。超过 40 字且包含多个动作时拆分。
- 操作使用「确认、创建、查看」等动词，不用被动句和名词化表达。
- 同一概念只使用一个称呼。英文标识保持大小写。
- 正文不用分号。连续出现三个「的」时改写。正文不使用破折号夹心解释：解释用冒号引出，或拆成两句。
- 相邻句子用因果、承接或对比关系连接，不用同义句重复中心。删掉一句后前后仍然通顺，说明这句只是重复。
- 删除「众所周知」「简单来说」「完全可以」等没有信息的修饰。禁用词以 `scripts/verify_content.py` 词表为准。

## 信息按动作排列

每个任务按「目标 → 执行 → 结果 → 必要解释」排列：

1. 先说明这一步要解决什么。
2. 给出最少命令或操作。
3. 给出稳定、可观察的成功结果。
4. 只解释继续操作所需的细节。

失败分支放到「常见错误」。可选说明放到任务末尾，或直接删除。删除后不影响首次成功的内容，不应出现在主线。凑字数句（统计性凑句、导航复述段）一律删除；删除判据见知识库 `bg-paragraph-list-style-v1`。

## 格式要降噪

- 命令、参数、路径、文件名和标识符使用行内代码；Ubuntu、Windows、VS Code 等平台名作普通名词时不加。
- 可复制命令使用指定语言的代码围栏，命令与输出分开。
- 标题和导航不使用行内代码。中英文之间保留空格。
- 列表用于并列或顺序关系。表格只用于比较允许多个属性的内容：同一主题的属性合并成一张表，不按小节拆成多张薄表；只有一两列信息或右侧大量留白时改用句子或列表。
- Callout 只放可跳过的提示，不承载必经步骤和唯一成功判据。

具体元素写法见 `references/quarto/authoring.md`，终端步骤见 `references/quarto/terminal-validation.md`。

## 写完后逐段删除

对每个段落依次检查：

- 删掉后影响当前任务吗？不影响就压缩或删除。
- 段落是否同时承担两个以上动作？是就拆分。
- 读者能否指出完成后要观察什么？不能就补结果。
- 正文、代码块和回顾是否重复同一句话？重复就只留一处。
- 新术语是否由当前动作自然引出？不是就后置。
