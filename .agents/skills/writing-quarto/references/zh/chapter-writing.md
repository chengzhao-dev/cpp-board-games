# 棋盘游戏章节写作

先遵循 `writing-principles.md`。本文件规定页面骨架的通用流程；本仓六段骨架的判定细节和井字棋各章职责，以知识库 `bg-chapter-page-pattern-v1` 与 `bg-engineering-storyline-v1` 为准，本文件不重复。

## 读者

读者有编程基础，可能第一次接触 C++ 工具链、CMake 工程或自动化测试。每页只解决一个任务。正文优先使用 C++20，构建环境以 WSL Ubuntu 为准，Windows 用于兼容性验证与浏览展示。

## 页面骨架

正文按下面顺序组织：

```text
无标题引言 → 任务序列（2-4 个 ##）→ ## 常见错误 → ## 自测问题 → ## 本章回顾
```

- 无标题引言承接上一章的结果（用章节标题链接），说明本章要解决的具体问题，交代整体认识与范围；不复述标题和命令，不放 Callout。
- `##` 承担一个可验证阶段，数量按独立任务和依赖关系决定；2–4 个是常见预算而非标题配额，`###` 只用于有独立动作或结果的子任务。`##` 下有多于一段的主线内容时必须拆成合理的 `###`，禁止「长导语 + 大段代码 + 过短 `###`」的失衡结构。
- 章目标与回顾分工：引言或紧随引言的目标节只陈述本章可交付、可见的产物，不提前堆「属于哪章、哪章再讲」的回顾式边界；「本章做到哪、后续章接什么」只写在 `## 本章回顾`，过程中的 `### 本章实现边界` 一类过程节标题一律不设。
- 每个任务按「做什么 → 执行什么 → 看到什么 → 简短说明」推进。
- 常见错误按症状分 `###`，标题后第一句写触发条件与可观察现象，正文给定位 → 修复 → 验证三个动作；入门章节只保留最可能遇到的 2-3 项。中间实现章的常见错误承接开发流程的报错记录（流程见知识库 `bg-engineering-storyline-v1`）。
- 自测问题用带 `.answer` 的有序「为什么」问题检查本章的关键因果关系；每章按关键因果关系决定题数，没有高价值问题时不添加，写法见 `references/quarto/authoring.md`。
- 本章回顾确认读者获得的能力并说明下一章可使用的状态；句数、句式与承接正文的要求以知识库 `bg-chapter-page-pattern-v1` 为准，不重复页面目录。

页面骨架的块级顺序与引言构成以知识库 `bg-chapter-page-pattern-v1` 为准。篇幅以知识库 `bg-content-budget-v1` 的 token 预算为准，由 `verify_content.py` 强制。

## 叙事范围（本仓硬边界）

本仓定位是完整 C++ 棋盘工程的用法与验收；C++ 语言机制的系统讲解由 cpp-notes 承担。`content/**` 正文因此只写五类内容：游戏语义、分层与依赖、接口契约、构建与测试验收、可验证动作。

- **禁止**用正文讲解 C++ 语言机制（枚举、结构体、命名空间、`inline`、`constexpr`、翻译单元、ODR 等），也禁止风格指南逐条教学（PascalCase、`k` 前缀、include guard 对比等）。
- **禁止**在正文写枚举成员释义表或释义段（如「每个状态码对应的局面：」加 `` `GameResult::kDraw`：棋盘下满… `` 列表）：不自明成员的含义用源码行尾注释承载，正文只写谁调用、如何验收、与邻章关系，不复述注释。规则见标识 `bg-comment-style-v1` 的知识文件。
- **禁止**在工程章（非 01 设计章）展开数值选型旁白：不写「用有符号整型承载…」「坐标字段为什么选定宽有符号整型…」，也不为选型链到 cpp-notes「类型安全与数值边界」。`int` 可出现在代码摘录中，旁白不解释「为什么有符号」。
- **禁止课堂类比**：工程坐标系、API 与数据结构只用程序事实与可观察行为表述，不写「数学课」「平面直角坐标系」等跨学科课堂对照（如「与数学课的直角坐标系正好相反」）。作者构思时可借类比想问题，落盘到 qmd 前必须换成工程对象与可观察行为；图注已交代原点与轴向的，正文不复述对照。
- **禁止突兀跨仓依据句**：不写「写法依据见 / 依据见 / 机制见 / 选型见 / 承诺见 / 用法见 / 陷阱见」+ cpp-notes。工程约定由本仓拥有；cpp-notes 是可选语言教材，不是工程写法的依据机关。
- **跨仓外链默认零条**。工程叙事须自洽。仅当本小节工程点已讲完、且确有系统学语法需求时，可在小节末**单独成句**尾置可选深潜，口吻为「若要系统阅读…，见 cpp-notes 对应章（GitHub 绝对 URL）。」同一章此类深潜宜 ≤2，能删则删。仅 01 设计章可保留一次分册级链接。本仓固定采用对方章的构建约定时，用「本仓固定采用…」陈述，仍放工程点之后，禁用「写法依据见」。
- **允许**代码块逐字展示源码（关键字照抄真实代码）；旁白回答工程问题：这段公共定义解决什么问题、谁读取或调用它、如何验证。
- **禁止接口清单压缩段**：不得把私有成员、公开成员名单、`const`、`[[nodiscard]]` 等接口属性压进同一段旁白；定稿形态为场景（动作 → 点名 → 边界）→ 代码 → 块后只补注释未覆盖的工程信息；语言属性不进旁白讲义（对照见标识 `bg-chinese-style-cases-v1` 的知识文件「接口清单压缩段」）。
- 判定口诀：句子的主语应是工程对象（棋盘尺寸、规则接口、头文件），不是语言构造（`enum class`、翻译单元）。反例与改写对照见标识 `bg-chinese-style-cases-v1` 与 `bg-project-decisions-v1` 的知识文件。

## 内容优先级

章节出现取舍时，按下面的顺序判断，不用较低层级的格式或样式要求覆盖较高层级的教学目标：

1. 读者任务与章节边界
2. 信息顺序和渐进披露
3. 页面块与段落布局
4. 技术正确性和可验证性
5. 标题、列表、Callout 和代码块等表达形式
6. 句子精简、术语和标点
7. 视觉样式与装饰

新增内容先确定它在既有页面块序列中的位置，再写入相邻小节。修改后回读完整小节及前后切口，确认动作、结果和下一步仍然相邻。只有步骤存在先后依赖时使用有序列表；同级选项使用无序列表；连续因果解释保留为短段落。

目录树先核对磁盘，再只保留当前任务需要的文件；树内文件用行尾注释交代职责，注释写成名词性职责短语（如 `# 顶层构建规则`），不用全角冒号挂解释，同一棵树语气一致；注释不点名下层具体文件名，`src/` 写“X 实现”，产物目录写存放物，文件分工留给讲实现的章节；树后不逐项复述，读法句直述机制、不用「X 回答 A，Y 回答 B」式问答并列。GitHub blob 链接嵌进同节导语句子里，不单独成行贴在代码围栏上方（细则见知识库 `bg-qmd-element-cases-v1`）。线性构建流程用标题和文字说明，不用 Mermaid 代替。

## 术语门槛

- 保留编译、链接、目标、状态、回合等标准术语；首次出现时用一句话解释或就近术语卡，再进入命令。
- 不解释对当前操作没有影响的内部格式。只保留判断成功所需的输出。
- 面向新人的正文不堆砌入门前置名词；标题只用读者此刻已认识的词。
