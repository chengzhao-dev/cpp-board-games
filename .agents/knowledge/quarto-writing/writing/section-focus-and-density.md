# 教学小节的主线收束与信息分层

本文件解释为什么一个小节要先闭合成功路径，再展开必要细节；执行细则见 `writing-quarto` 技能 `.agents/skills/writing-quarto/references/zh/section-focus-and-density.md`。页面块的整体顺序见标识 `bg-chapter-page-pattern-v1` 的知识文件。

## 页面宽度与垂直节奏

页面“紧凑”通常有两个来源：正文列太窄导致无谓换行，或块之间缺少承接留白。优先小幅放宽 Quarto HTML grid 的 `body-width`，再用共享 CSS 调整正文块间距；不要只放大字体，也不要用局部规则给每个块重复加 margin。正文列仍需保留 `max-width: 100%`，代码和宽表在窄屏上继续滚动或换行。

当前仓库采用 720px 的正文列和约 1.55rem 的普通块间距，代码块连续出现时保留更大的间隔。评估重点是：每个任务是否有清晰的动作与结果、连续盒子之间是否有解释段、移动端是否出现横向溢出。这里不设置依赖浏览器截图的硬阈值，最终以 `quarto render` 后的 HTML 结构和实际阅读抽查为准。

Quarto 通过 HTML grid 控制正文、侧栏和目录列，代码块的 `filename`、换行和复制行为由代码块配置及 CSS 共同控制；页面宽度与代码标题过长是两个独立问题。

## 一图一事与同主题相邻

图是读者视觉负荷最高的盒子：一张图同时表达两条关系时，读者要同时在脑子里维护两个对照，图前正文与图后结论也各要写两遍才能闭环。因此一张图只核对一条已讲清的关系，需要两条就拆图或拆节。代码与图相邻的前提是同一对象：图讲 B 而前后代码讲 A、C 时，读者被迫在三个对象间跳转，这正是「代码 A → 短句拐弯 → 图讲 B → 再贴代码 C」式堆叠的成因。主题错位时先用一句正文收束本对象，再另起 `###`。图中的每个框和箭头都应能在图前正文找到出处；图引入正文没有的概念时，读者只能靠猜。写法见 `writing-quarto` 技能 `references/quarto/authoring.md`「代码与图的桥接」。

## 主线必须先闭合

读者在教程中需要不断确认"我现在做什么"和"我是否做对了"。如果命令、输出、参数解释和下一步背景交错出现，读者必须频繁切换目标，无法判断哪一块是必经步骤。先给唯一动作和可见结果，再补解释，能把首次成功压缩成一条可回放的路径。

主线闭合要求一节只有一个要闭合的目标：标题、第一句、动作和验收输出指向同一个结果，中途出现第二个独立动作时，读者就无法判断当前在等哪一个。任务粒度本身的判定标准属于页面结构，见标识 `bg-chapter-page-pattern-v1` 的知识文件。

标题对齐同时排除离题辩白：操作小节里出现与标题无关的工程取舍长论（「为何不跳过某步 / 幂等 / 配置漂移」类），读者在动作中途被要求读辩白，主线同样被打断；删除后不影响首次跑通与验收的整段删除，确需保留的归属对应排查节。执行规则见标识 `bg-paragraph-cohesion-v1` 的知识文件。

当多个 `###` 共享同一阶段、环境或产物时，可以用父级 `##` 统摄，但父级只负责分组，不能把两个各自可验收的任务压成一个模糊标题。父标题要写清当前阶段或范围，子标题继续使用可执行、可观察的任务名。

## 长段拆分的判断依据

长段的问题不在于占据多少行，而在于它要求读者同时记住多个职责。主线动作、成功判据和可跳过说明压在同一段时，只读必要内容的读者必须重新寻找下一步，逐字阅读的读者又无法判断哪些细节可以跳过。按职责拆成短段，能让首次执行和回看细节两条路径自然分开。

普通 Callout 不能成为细节垃圾桶。把可以跳过的内容集中进提示框后，读者仍要判断这段是否影响当前任务，而且视觉上独立的盒子容易像必经步骤。只有删除后不影响首次成功和验收的信息才适合下沉，并且每个任务最多保留一个尾置 Callout；术语解释型 Callout 是就近放置的例外，写法见标识 `bg-qmd-element-cases-v1` 的知识文件。稳定界面判据与它的解释同框时，另见下节约束。

合并与拆分都按信息职责判断，不按固定字数。同一状态内部的账号创建和正常现象可以合并。成功判据与后续执行范围进入下一个状态时另起一段，即使它们仍属于同一次首次启动流程。

## 正文与 Callout 的重量平衡

读者会把长而密的正文当成当前主线，把紧随其后的短提示当成脚注。正文同时承担先后状态、正常现象、成功判据和执行范围，而 Callout 只剩一句术语解释时，两者的信息重量差距过大，新手容易跳过提示，之后又把提示符误解成命令行语法。

修法必须同时发生。正文按状态节点拆短，让每个状态节点各有落点。Callout 恢复并列字段的列表结构，让内容本身具备可扫读的重量。只放大 Callout 会让所有可选提示都像重点，只拆正文又会让尾部提示继续像脚注。必经动作始终留在正文。成功判据只有在不要求读者继续操作、且需要根据所见界面继续解释时，才可以和解释组成结果型 Callout。

## 结果型 Callout 的边界

把提示符判据留在正文，再把符号含义放进 Callout，会把同一个观察对象拆成两处：读者先看到一个结论，跳过提示框后又不知道如何理解它。把两部分都塞回正文，则会让结尾重新变成长段。结果型 Callout 解决的是这种"判据本身也是解释对象"的局部问题，不是把成功路径移出正文的通用许可。

使用时必须同时满足四点：成功判据是稳定、可直接观察的界面或状态。判据需要继续拆解字段、范围或含义。提示出现后本任务没有其他必经动作。正文已经用检查动作和明确的前瞻完成交接，且 Callout 首句直接兑现该检查动作。若后续还要输入命令、做选择或根据结果修复，判据必须留在正文操作位置。

"含义和范围如下"只说明后文目录，没有告诉读者要对照什么。Callout 再从"出现……"重新建立条件，会让同一次判断被拆成两次起句。改写时，正文提出"请对照下面的格式确认结果，并了解后续范围"，Callout 首句直接给出"看到……说明……"。正文负责建立检查动作，Callout 负责呈现判据，二者接力而不重复全文。

## 命令、输出与细节各司其职

命令是输入，输出是观察，正文是判断依据。三者混在同一个代码块或连续多个解释段落中，会让读者自己筛选"哪些行要复制、哪些行只是说明"。因此闭环目标、命令和成功判据各保留一个权威位置，操作小节拥有命令与验收，回顾和相邻段落只补充新增信息。路径、版本号等随环境变化的输出应展示可识别的典型形态，并给出"每项都有非空结果"这类稳定判据，而不是要求逐字匹配示例。成功判据还必须与证据层级相称：路径只能证明命令可定位，不能直接证明工具功能正常，功能结论应由对应的实际操作支持。

## 盒子与正文的比例

盒子指代码块、表格、提示框、引用块、图表容器，含 `{mermaid}` 图与 `{python}` 坐标图单元。它们底色与边框一致、左右内缩相同，连续出现时读者分不清内容边界，只能靠滚动位置感知，页面从「读一段做一步」退化成「抄一屏」。因此一条主线动作配一段自己的承接正文：单个 `##` 的主线盒子控制在两个左右，相邻盒子最多一处，其余被正文隔开。每两个盒子之间至少有一段交代判断依据的话；代码块与图之间的固定桥接序列见标识 `bg-qmd-element-cases-v1` 的知识文件。

修法是补承接正文，而不是删盒子。盒子承担可复制性，正文承担判断依据，两者不可互换，代码块删到只剩命令不会自动产生判断依据。

代码块前后的文字重量也应服务同一个任务闭环。代码块前至少说明读者要完成什么、在哪里执行以及执行后会发生什么；代码块后只说明下一步、可观察结果或一个必要的新人解释。若提示符、参数含义等补充信息不影响主线执行，可在主线结果确认后放进一个短 Callout；Callout 只解释新信息，不再复述命令、重启动作或成功判据。

密度比例不设硬阈值。盒子多少、正文长短同时取决于视口宽度、字体度量和 Quarto 版本的 DOM 结构，任何一项变化都会让历史数值失效，基于 DOM 或截图的硬编码闸门只会在与密度无关的改动上误报，仍然禁止。`verify_content.py` 保留一条软闸门：同一小节内两围栏（含 `{mermaid}` 与 `{python}` 单元）之间只有空行、没有桥接正文时报 WARN，提示人工补承接句；WARN 不判失败，人审与对照案例仍是叙事的主闸。

## 元素边界

细节只有拥有独立输入、动作和验收结果时才升级为标题，否则留在当前小节的延伸区域。常见错误使用三级结构，是因为目录负责导航、具体症状负责识别、有序步骤负责操作。具体写法见标识 `bg-chapter-page-pattern-v1` 与 `bg-qmd-element-cases-v1` 的知识文件。

这种分层与页面整体的六段块序列并不冲突：它只收束任务段内部的阅读路径，不重新定义引言、任务序列、排查、自测和回顾的页面职责。

## Callout 尾置的原因

Callout 是视觉上独立的盒子。把它插在段落、命令或输出之间，会让读者误以为提示框也是必经步骤，主线因此被切断。可跳过内容在成功路径闭合后再出现。影响当前操作的内容不能靠提示框隐藏。术语解释型 Callout 是唯一就近放置的例外：它解释读者正看着的对象，拖到任务末尾反而切断对应关系。

"目标 → 动作 → 结果 → 补充"能同时照顾首次执行和回看细节的读者。它把必须完成的内容放在主线，把可选解释放在尾部，也避免在开头只有一句目标、末尾却集中堆叠参数和手册链接。

## 目录树只展示当前任务需要的文件

目录树先尊重磁盘事实，再删除不影响当前任务的缓存和构建产物。`build/` 是否展开取决于当前任务是否需要认识产物的位置：布局章展开 `bin/` 与 `lib/` 建立完整目录认知，验收章展开它核对产物；只讲源码的章节保持折叠。

正文只强调读者当前需要识别的文件。目录树后的说明不复述每一行注释。展示顺序按工程理解推进：接口与实现（源码）、构建规则、测试与运行产物；实现章正文按同一顺序展开叙事，设计与实现先于构建规则，再进入测试（顺序见标识 `bg-chapter-page-pattern-v1` 的知识文件）。

树内行尾注释承担文件职责说明：每个展示文件都有行尾注释，一短语一职责，不在树内展开解释。树后不再用列表逐项复述注释；GitHub 链接放在该文件首次被精讲的正文处。与主线无关的子目录折叠为单行目录，不展开子文件。

正式 C++ 入门页不用 Mermaid 表达线性构建流程，改用标题和文字连接。复杂数据流确实难以文字说明时，才使用独立图表并给出一句结论。

## 行内代码只标记需要逐字识别的对象

命令、参数、文件名、路径、配置键、API 和标识符使用行内代码。Ubuntu、Windows 和 VS Code 作为普通平台名称时不加反引号。标题与导航不使用行内代码。

同一对象在同一页保持一种标记方式。链接标签内不再嵌套行内代码。行内标记连续出现时，改用完整句子减少读者来回切换字体。

标记边界与术语节奏的执行规则见标识 `bg-chinese-style-cases-v1` 的知识文件，本文件只解释为什么需要克制。
