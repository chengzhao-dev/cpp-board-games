# 中文技术写作的句段与措辞案例

依据 cpp-notes 仓库 `chinese-style-cases.md` 适配本仓库，保存段落、句子和措辞的正反对照。低频的章级定稿对照在 `appendix/chinese-style.md`（不进检索索引，仅人审时读）。

## 正确形态正例

不需要改写的正确形态长这样，写正文时可直接对照：

```text
正确（段落导语：工程语境 + 一句判断依据）：
这段构建规则定义可执行目标 app：先规定产物目录，再列出源文件，最后声明 C++20。
三条命令各管一步，读者按顺序核对即可。

正确（收束句：指向可观察结果）：
看到 Hello, World! 后，就完成了本章的实践目标。

正确（排查句：可核对的排查范围）：
第一次配置、编译、测试失败时，排查范围限定在工具链与构建规则；工程不含游戏逻辑。
```

正例的判定条件：主语是工程对象；一句话一件事；验收句指向能看到的结果而不是宣告章节状态。

## 长句与连接关系

连接词必须表达真实因果、时序、转折或条件。一个句子出现三个以上动作、多个「并且」或多个括号时拆分，并保留明确主语：

```text
不佳：完成 A 后通过 B 使用 C，并根据 D 判断 E，最后处理 F。
改写：完成 A。接着使用 B 执行 C。根据 D 检查结果，满足条件后处理 F。
```

需要一句话交代多个条件与同一结果的对应关系时保留长句，拆开反而让读者在短句间拼接。

## 分号与句长

```text
不佳：先执行 A；再执行 B；完成后检查 C，不通过时回到上一步。
改写：执行 A，再执行 B。完成后检查 C。不通过时回到上一步。
```

## 罗列短句成段

以 01 章「观察一局对话」改稿前为对照。三个短句各自成立、句间无衔接，读起来像清单；分号还把显示棋盘与拒绝非法输入两件事串进一句（规则见标识 `bg-paragraph-list-style-v1` 的知识文件「罗列短句成段禁令」）：

```text
不佳（三个独立短句堆成一段，句间无衔接；分号串两个中心）：
两名玩家轮流在 3×3 棋盘上落子。程序显示棋盘并提示下一位玩家；输入越界、占用或格式错误时说明原因并保持棋盘不变。

改写（一个中心主题，衔接词组织成连贯句，分号改写）：
两名玩家轮流在 3×3 棋盘上落子：程序每一轮都先显示棋盘，再提示接下来轮到谁。输入越界、占用或格式错误时，程序会说明原因并保持棋盘不变，要求重新输入。
```

判定信号：段内句子逐句可删、互不引用；句间没有承接、因果或时序词；删掉分号后的任一分句中心仍成立。真正并列、需要扫读的项改用列表，不做伪连贯。

## 导语多中心与分号挂外链

块前导语只引出紧随的代码块；跨仓外链默认不写，若保留须工程点讲完后尾置（硬边界见标识 `bg-paragraph-cohesion-v1` 的知识文件）。以 03 章对局玩家与棋盘格子状态节改稿前为对照：

````text
不佳（导语一句挂两个中心，分号再挂外链，读者分不清这句在引代码还是在引参考）：
对局玩家与棋盘格子状态分别描述参与者和棋盘取值，库对外头文件定义两者；枚举类型的语言机制见 cpp-notes 枚举章：

```{.cpp filename="board.h"}
（Player 与 CellState 两套枚举）
```

改写（导语只保留一个中心，冒号引出代码；默认不挂外链）：
board.h 用两套枚举区分对局身份与棋盘格子状态：

```{.cpp filename="board.h"}
（Player 与 CellState 两套枚举）
```
````

判定信号：删掉分号后的任一分句，句子中心仍然成立，说明原句是多中心句；口诀见 `writing-quarto` 技能 `references/zh/writing-principles.md`。

## 突兀跨仓依据句

工程章正文禁止把 cpp-notes 写成「写法依据」插进工程句中间。以 03 章棋盘尺寸节改稿前为对照：

```text
不佳（工程句做到一半插入姊妹仓「依据」，像粘贴补丁）：
头文件里的常量统一写成 `inline constexpr`，写法依据见 cpp-notes 常量与 constexpr。

不佳（列表项尾挂「陷阱见」选型外链）：
`kCellCount`：……有符号乘法在拓宽处的陷阱见 cpp-notes 类型安全与数值边界。

改写（删依据句与选型链；源码摘录已展示 `inline constexpr`，旁白只写谁调用、如何验证）：
（删除整句；列表项只保留工程职责，不挂 cpp-notes。）

可选尾置（仅当该小节工程点已讲完且确需系统学语法时，单独成句）：
若要系统阅读枚举类语法，见 cpp-notes 枚举类章。
```

判定信号：句中出现「写法依据见 / 依据见 / 机制见 / 选型见 / 承诺见 / 用法见 / 陷阱见」+ cpp-notes；或工程约定尚未讲完就跳转姊妹仓。`verify_content.py` 对上述句式判失败。

## 冒号后堆叠分号解释

冒号引出解释后还用分号续接第二个解释，是把两个中心压进一句。以 03 章落子局面图后句与 `CellStateFor` 段改稿前为对照：

```text
不佳（图后句先复述 Move 的字段构成，冒号后堆图内局面作第二主题）：
一次 Move 只携带目标棋盘格子坐标与对局玩家两个字段：图中 (1,1) 与 (0,2) 已落下棋子，加粗框指向的棋盘格子就是下一个 Move 的 position。

改写（删字段复述，图后两句短句各一中心）：
图中 (1,1) 与 (0,2) 已落下棋子。加粗框指向的棋盘格子就是下一个 Move 的 position。
```

```text
不佳（冒号引出解释后用分号堆叠身份区分与使用方）：
CellStateFor 回答“对局玩家应写入的棋盘格子状态是什么”：Player 表达对局身份，CellState 表达棋盘格子状态，两者互不替代；把身份翻译成棋子只在这一个函数发生，规则判定与显示都消费它的结果。

改写（独立短段三句，每句一中心，全程无分号）：
CellStateFor 负责把对局玩家翻译成棋盘格子状态。对局身份与棋盘格子状态互不替代，这个翻译只发生在这一处。规则判定与终端显示都读取它的返回值。
```

判定信号：冒号后的解释超过一句还用分号续接；图后句或函数段删掉任一分句后中心仍成立。

## 破折号夹心句

正文用破折号夹住解释时，读者要在一句话里跳进跳出两次。正文停用破折号，解释用冒号引出或拆成两句，规则见标识 `bg-paragraph-list-style-v1` 的知识文件：

```text
不佳：src/main.cpp：被编译和运行的程序——输出一行稳定文本并返回 0；
改写：src/main.cpp：被编译和运行的程序，输出一行稳定文本并返回 0；

不佳：脚本每次都重新执行配置，而不是判断 build/ 已存在就跳过——配置是幂等的。
改写：脚本每次都重新执行配置，而不是判断 build/ 已存在就跳过。配置是幂等的。
```

## 措辞替换

| 不佳表达 | 改写 |
| --- | --- |
| 对文件进行修改 | 修改文件 |
| 如果……的话 | 如果……，或……时 |
| 其实/简单来说/完全/非常/特别 | 删除，不保留无信息修饰 |
| 吃透/讲清/彻底理解 | 改成可观察的验证结果 |
| 错误被返回 | API 返回错误 |
| 刻意保持最小 / 刻意…… | 直接陈述程序做了什么、不包含什么 |
| 只可能来自 A，不可能来自 B | 写成可核对的排查范围：工程不含 B → 失败时先查 A |
| 由 N 段命令定义：A、B 和 C | 用职责顺序：先 A，再 B，最后 C |
| 规则库 | 井字棋动态库（读者正文与代码注释、CMake 注释统一此定名） |
| 即胜着 / 更好的着 / 随机着法 | 马上能赢的一步 / 对当前玩家更有利的一步 / 随机落子 |
| 占格落子 / 占格 | 向已有棋子的格子落子 / 已占用 |
| 行优先（读者正文） | 按行依次排列；涉及下标用区间表述（第 0 行占下标 0–2） |
| minimax（读者正文） | 极小极大 |

## 可能性断言与作者姿态

诊断与范围用可观察事实，不用「只可能 / 不可能」式假确定性，也不用「刻意」等作者姿态修饰：

```text
不佳：程序刻意保持最小，只向标准输出写一行固定文本并返回 0。第一次配置、编译、测试如果失败，原因就只可能来自工具链，不可能来自游戏逻辑。
改写：它只向标准输出写一行固定文本并返回 0，不含任何游戏逻辑。第一次配置、编译、测试失败时，排查范围限定在工具链与构建规则。
```

```text
不佳：可执行目标由三段命令定义：输出目录、源文件清单和语言标准：
改写：这段规则定义可执行目标 app：先规定产物目录，再列出源文件，最后声明 C++20。
```

## 渐进披露元叙述

把 Agent 侧的写作策略念给读者听，是典型的 AI 味元叙述。正文直接陈述对象和结果，延后的内容保持沉默：

```text
不佳：语法细节留到后续章节真正用到时再展开。本章只需认清这段程序里被下游读取的两处结果：标准输出中的 Hello, World!，以及 main 返回的 0。
改写：这段程序对外可见的结果只有两处：标准输出中的 Hello, World!，以及 main 返回的 0。
```

判定信号：句子的主语是「本章 / 这本书 / 写作策略」而不是工程对象；内容在告诉读者「接下来不讲什么、什么时候才讲」。禁用词见标识 `bg-terminology-v1` 的知识文件。

不整词禁用「可能」：规划边界可写「按需评估」；技术命题「不可能改变结果」改为肯定表述（如「跳过不改变搜索结果的分支」）。

## 指代与验收

已知对象名称时直接复用对象名（`这个程序` → `Hello, World! 示例程序`）。验收句指向可观察结果：`看到 Hello, World! 后，就完成了本章的实践目标`，不写 `本章就完成了`。

悬空指代与笔记腔：

```text
不佳：划定了这条路线的边界。……与这条流程直接相关的只有两个文件……，下面分别精读。
改写：先看清工程确认了工具、项目内容与分层实现。……src/main.cpp 与 CMakeLists.txt 是配置与运行的两个关键文件。
```

```text
不佳：本章配置和运行的对象就是引言中的最小工程目录……代码块标题使用短文件名……避免标题栏被深层路径挤满：
改写：最小工程目录如下，树内注释标出各文件职责。src/main.cpp 与 CMakeLists.txt 是配置与运行的两个关键文件。
```

## 术语节奏

首次出现时就近放术语 callout（规则见标识 `bg-chapter-page-pattern-v1` 的知识文件），后续固定一种称呼。普通概念不加行内代码；命令、路径、文件名、关键字、API 和配置键使用行内代码。同一对象在同一页保持一种标记方式，链接标签内不嵌套行内代码。

一个概念全书只用一个词，统一术语与替换规则见标识 `bg-terminology-v1` 的知识文件。对照案例：02 章引言「本章开始第一个实现切片」先改「本章开始第一个阶段」，同日二次修订后「阶段」统称一并停用，正文直接写具体目录路径。

## 同一决策合并成段

换源原因、版本差异、配置路径差异属于同一决策，合并成一段；把同一对象拆成「目录如下。命令都在这里执行。」两个短句会制造停顿，直接写成一个动作句：`下面的目录是本章示例的文件清单，所有命令都在该工程根目录执行。`

## 多命令讲解改列表

以 02 章注册冒烟测试节为对照；同日二次修订，一段一命令的拆分形态推翻为列表（规则见标识 `bg-paragraph-list-style-v1` 的知识文件）：

```text
不佳（一段四句：三条命令 + 与节首重复的总结）：
enable_testing() 开启 CTest……。add_test 用 NAME 和 COMMAND……。set_tests_properties 再加一道……。三条命令合起来定义了本章唯一的自动化检查……。

改写（列表：行内代码标识符 + 一句职责，描述从简）：
- enable_testing()：开启 CTest，此后注册的测试才能被发现和运行。
- add_test()：把可执行目标注册成名为 app_smoke 的测试。
- set_tests_properties()：要求输出匹配 Hello, World!。
```

总结句「三条命令合起来定义了本章唯一的自动化检查」与节首句「同一份构建规则还注册了本章唯一的自动化检查」重复，按同义反复禁令删除；节首句同时充当列表引言。段间衔接见标识 `bg-paragraph-cohesion-v1` 的知识文件。

## 相邻段落同义合并

以 02 章理解最小程序源码节为对照。相邻两段各自换一种说法讲同一事实（程序对外可见的结果 / 自动化检查针对的结果，都是「输出含约定文本 + 退出码 0」），合并为一段：

```text
不佳（双段两说，第二段只是换主语复述）：
这段程序被下游读取的结果只有两处：标准输出中的 Hello, World!，以及 main 返回的 0。

构建规则里的自动化检查针对这两处：输出须含约定文本，进程须以退出码 0 结束；两处同时满足才算通过。

改写（一段点名成功条件，机制留给冒烟测试节映射）：
这段程序的成功条件只有两条：标准输出须含约定文本 Hello, World!，进程须以退出码 0 结束；自动化检查要求两条同时满足。
```

判定信号：两段删掉任意一段、主线仍闭合；第二段的主语换人（程序 → 检查），谓语与对象不变。合并后其余位置不再以第三种说法复述。

## 多问一答拆成引言—列表—收束

以 02 章自测「配置和构建分别由哪个工具完成」为对照。一段同时回答谁做配置、谁做构建、何时重配时必须拆开（规则见标识 `bg-paragraph-list-style-v1` 的知识文件）：

```text
不佳（一段压三问）：
配置由 CMake 完成：读取 CMakeLists.txt，在 build/ 下生成构建计划。构建由 Ninja 完成：按计划把源码编译成可执行文件。所以改了 CMakeLists.txt 要重跑配置，而只改 main.cpp 时重新构建就够了。

改写（引言 → 引导词列表 → 收束）：
配置和构建是两件不同的事，由不同工具完成。

- **配置**：由 CMake 完成，读取 CMakeLists.txt，在 build/ 下生成构建计划。
- **构建**：由 Ninja 完成，按计划把源码编译成可执行文件。

改了 CMakeLists.txt 要重跑配置；只改 main.cpp 时重新构建即可。
```

## 口语开场与规划套话

语气与语域的完整标准见标识 `bg-chinese-voice-register-v1` 的知识文件；以下两例是重构井字棋全书时的定稿对照。

开场把讲义口换成书面陈述（01 章）：

```text
不佳：井字棋动手前先弄清三件事：用哪些工具、项目要处理哪些内容、代码按什么层次实现。
改写：进入井字棋实现前，先确认三件事：使用哪些工具、项目要处理哪些内容、代码按什么层次实现。
```

引言把元叙述换成三句：承接上一章、这一章要交出的结果、对应源文件。源文件用中文锚文本的 GitHub 链接给出，不写行内代码路径：

```text
不佳：本章让单次动作可靠起来，先明确交付的行为与测试边界；内容的落点是 games/tictactoe/03-move-validation/…目录在真实开始实现时创建。本页是规则设计页，尚未对应可运行的实现目录。
改写：棋盘与状态建立了状态模型。本章定义单次落子的合法与非法处理及其测试边界；对应实现在 [落子合法性实现目录](https://github.com/chengzhao-dev/cpp-board-games/tree/main/games/tictactoe/01-cli-game)，实现并通过验收前按设计页阅读。
```

## 目录式堆砌

一句里串多个交付物或动作时，读者拿不到「本章唯一结果」，正文退化成说明书目录（删改口诀见 `writing-quarto` 技能 `references/zh/writing-principles.md`）。两个 canonical 反例来自 03 章改稿前的原文：

```text
不佳（章引言交付物清单，一句串四个交付物）：
本章把规则核心拆成独立组件并编译成动态库，定义棋盘与状态的值类型，
固定查询、落子与结果三个入口，并引入 GoogleTest 编写规则测试。

改写（引言只承诺一个可验证结果，细节进小节）：
本章把规则核心编译成动态库，并用 GoogleTest 固定状态接口的行为。
```

```text
不佳（树后说明书复述，逐项重讲树注释已交代的职责）：
规则库组件 tictactoe/、终端程序组件 apps/ 与测试目录 tests/
各自带 CMakeLists.txt，顶层规则只做工程声明、产物目录与组件组合。

改写（删复述，至多一句关系收束）：
三个组件各自带构建规则，由顶层规则组合成一个完整工程。
```

判定信号：把隐喻词删掉后读者说不出这句话约束什么、产出什么，或主语是缩写、谓语缺对象（「CLI 打印」「CLI 报错」）。编写者之间的沟通文档（.agents/**）不受本条限制，但不得把这类写法教成读者的正例。

## 零基础可懂的读写路径与层名定义

讲「谁改棋盘、谁读结果」时不用架构隐喻句（「经规则接口读写」「状态不反向依赖调用者」），按三步模板写：先说屏幕上或调用处发生什么，再点名类型与函数，最后一句边界。正例模板（03 章定稿）：

```text
正确（先动作 → 再点名成员 → 后边界）：
终端程序把「行 列」变成一次落子动作后，只能调用 Game 的三个成员去改棋盘或查结果，
不能直接改私有数组 cells_。测试也调用同一组成员。
Game::Place 负责写入棋盘格子；Game::CellAt 负责读某个格子；
Game::Result 负责报告整盘是否已结束。
```

```text
不佳（隐喻句，读者还原不出画面）：
棋盘状态经规则接口读写，状态不反向依赖调用者，动作只从外部进入。
改写（写成上模板的成员清单）：
终端程序与测试都只调用 Game 的三个成员读写状态；
Game 不调用终端程序，也不读键盘。
```

架构层名（终端适配层、规则核心、规则接口）可保留，但首次出现必须用一句可观察行为定义；Mermaid 图节点用日常说法（如「终端程序」「规则库里的 Game」），图后列表再对上术语：

```text
正确（层名首次出现给可观察定义）：
规则接口是 Game 暴露的三个成员函数，终端适配层负责把键盘输入翻译成 Move。
```
