# 统一注释风格规范

本文件是全仓库生成和评审注释的唯一基准，覆盖 C++、Bash、CMake、YAML（`.clang-format`、`.clang-tidy`、`.clangd`）、JSONC（`.vscode/*.json`）、TOML（`config.toml`）、点文件（`.gitignore`、`.gitattributes`、`.editorconfig`）和 Python。Agent 生成任何代码或配置注释时必须遵循本规范。2026-09 依据 LLVM、Google C++、Google Shell、Linux 内核、PEP 8/257 等公开标准联网核实后沉淀，来源见文末。

## 分段基准与内容原则

- **分段形式**以 LLVM 为基准：文件头和段落用定宽 `===` 横幅分隔。
- **注释内容**以 Google 为基准：解释意图与取舍，不逐行复述代码；"不要事事注释"，只注释不显而易见的部分。
- **注释不承载规范说理**：命名惯例、官方建议（如「CMake 官方不建议 file(GLOB)」）、未来演化指引（如「将来改成 PUBLIC」）、外部规范引用（clig.dev、Google Shell）一律不写进代码注释；面向读者的说理进 Quarto 对应章节的 callout，面向作者的论证进 `.agents/knowledge/`。注释只回答「这段代码做什么、有什么关键约束」。
- Linux 内核的 `/*\n * ...\n */` 盒式注释仅适用于 C，本项目不采用；OpenAI 无公开注释风格指南，不作为依据。

## 语言注释符

| 文件类型 | 注释符 |
| --- | --- |
| C++（.cpp/.hpp） | `//`，不使用 `/* */` 盒式注释 |
| Bash（.sh） | `#` |
| CMake（CMakeLists.txt） | `#` |
| YAML（`.clang-format`、`.clang-tidy`、`.clangd`） | `#` |
| JSONC（.vscode/*.json） | `//` |
| 严格 JSON（compile_commands.json 等） | 禁止任何注释 |
| Python | docstring（`"""`）+ `#` |

## 注释层级与职责

注释按读者需要的信息分三层加一类函数契约，不用同一段文字同时承担文件说明、代码分组和规范论证：

| 层 | 写什么 | 不写什么 |
| --- | --- | --- |
| 文件头横幅 | 文件是什么 + 读者可直接理解的用途（1–3 行） | 版权、作者、日期；「探针」「阶段」「领域值类型」「存储抽象」等读者黑话；规范说理 |
| 职责段横幅 `#===...===#` | 只标大职责块名（如「严格模式与工作目录」「可执行目标」「测试」） | 意图、参数含义、失败处理、论证；冒号后的步骤链 |
| 普通邻接注释 | 紧随其后的代码的关键约束或失败后动作，≤2 行；多标志命令必须写明这些标志改变了什么 | 复述命令字面；「为什么不用某写法」的长论证；颜色/TTY 展示细节；只说「重新配置」却不点名生成器、编译器或编译数据库 |
| 函数注释（Bash 等） | 1–2 行关键约束：结果写到哪一路、失败后做什么 | `Arguments:` / `Outputs:` / `Returns:` 清单；把函数体里已经看得见的 `printf` 再写一遍 |

短文件（约 ≤20 行）只写文件头，不加段横幅。段横幅只划分工程声明、目标、测试或脚本步骤等大职责块。

多标志命令的注释要短，但必须能核对。`cmake` 配置行上方写明生成器、编译器、构建类型和 `compile_commands.json`，并写明每次都重新配置，避免这些开关留在旧缓存里。换编译器时删除 `build/` 的完整排查步骤写入 Quarto 或本知识文件，不在脚本旁展开。

禁止错配：几行就能读完的辅助函数配上 `Arguments:` / `Outputs:`，而真正决定构建结果的命令只留「使脚本里的参数进入当前构建计划」这种空话。函数体已经写出 `printf` 的去向时，不再单列参数和输出清单。正反对照见 `cpp-teaching/cases/comments.md`（标识 `bg-comment-cases-v1`）。

## 邻接单行注释：一注一句

并列语句需要注释时，一句注释只标紧随的一条语句，注释与代码之间不空行；不是每行必注，没有独立意图的语句不加：

- 正确：每条语句正上方一行意图注释（如产物目录的三条 `set` 各配一行）。
- 错误：一行注释覆盖后面多条兄弟 `set`/命令——读者对不上哪句由哪条注释负责。
- 注释与命令错位同样不行：注释写「链接规则库」却放在 `add_executable` 上方，链接命令反而无注释，是「一注多句」的变体。
- 不改范围：文件头与 `#===` 段横幅、枚举行尾注释、单命令 ≤2 行折行注释不受本条约束；语义上不可拆的单个操作（如 `FetchContent_Declare` + `FetchContent_MakeAvailable` 成对完成一次拉取）可共用一行注释。

源码与 Quarto 摘录同源同规：摘录片段逐字取自源文件，源文件改成「一注一句」后摘录自然继承。正反对照见标识 `bg-comment-cases-v1` 的知识文件「一注多句对照」。

## 枚举与常量行尾注释

- 类型意图写在 enum 定义上一行（如 `/// 棋盘格子的状态。`，声明注释的 Doxygen 标记见「多行注释」）；类型注释只写一句整体含义，不列举成员取值——成员语义由各自的行尾注释承担（`GameResult` 判例：类型注释收口为「对局的结果。」，用户定案）。成员行尾注释只在成员名不能让初学者直接对应领域语义时才写，避免把同一信息重复多遍。
- 需要行尾注释的成员用 Doxygen 行尾形式加简洁词（如 `kEmpty = 0,   ///< 空格。`；行尾成员文档在标记后加 `<`，语法见来源 Doxygen 手册，OpenCV 头文件用同义的 `//!<` 形式）；类型上一行已含「棋盘格子」锚点时，成员行尾不写「空棋盘格子」。多条行尾注释时 `///<` 列对齐，且整行不超 `ColumnLimit: 100`（对齐由 Google `BasedOnStyle` 的 `AlignTrailingComments` 承担）。
- **语义结果优先**：不自明成员的行尾须先写出读者不识英文名也能懂的结果词（如 `平局`、`游戏进行中`、`X 获胜`），判定条件可选跟在全角冒号后（如 `///< 平局：棋盘下满且无人三连。`）。禁止只写条件、不写结果（读者从 `kDraw` 的「棋盘下满且无人三连」对不上「平局」）。结果词与程序输出文案统一：`kInProgress` 行尾注释与 CLI 结果短语同用「游戏进行中」，不用裸「进行中」（用户定案）。
- 同一 `enum` 内要么全部成员都有行尾注释、要么全部没有，禁止半套：部分成员有、部分没有会让读者怀疑漏写。`CellState` 定案**全量**行尾注释（`kCross`/`kNought` 需翻译为 X/O 棋子，且与 `Player` 的同名成员异义）；`Player` 定案**全量**（`kCross` 行尾「先手：使用 X 棋子。」、`kNought` 行尾「后手：使用 O 棋子。」——先手后手与棋子归属是类型注释「对局玩家」装不下的领域语义；棋类行话「执 X/O」禁用，读者对不上「执」对应什么动作）；成员语义确已由类型注释承担的枚举（如 `Strength` 的三种强度）才一条都不写。
- `struct` 数据字段的行尾注释与枚举成员同规：字段名不能直接对应领域语义或需补充约束时才写，写了就全量——`CellPosition` 的 `row`/`col` 定案全量（`///< 行坐标。`/`///< 列坐标。`），`Move` 的 `position`/`player` 同款全量（用户定案）；全自明字段一条不写。
- 井字棋领域注释保留现实锚点：单格写「棋盘格子」，`CellPosition` 写「棋盘格子坐标」，`CellState` 类型注释写「棋盘格子的状态」，`Player` 写「对局玩家」。`CellPosition` 注释只写坐标含义，不写「用有符号整型承载」等选型旁白；选型旁白禁令的完整表述见下文「类型选型与组织自述不进注释」。
- 正反对照见标识 `bg-comment-cases-v1` 的知识文件「枚举行尾注释对照」。

## 类型选型与组织自述不进注释

注释只写读者理解对局语义所需要的信息（Google 的「Optimize for the reader, not the writer」原则：读代码的时间多于写代码的时间）。两类内容默认不进注释：

- **类型选型旁白**：宽度、拓宽、承载与转换细节（如「同为 int32，乘积不再拓宽」「只在结果上转成 size_t」）不写——类型在代码里已经可见，初学者读的是对局语义。整型乘加的做法本身仍按标识 `bg-google-cpp-style-v1` 的知识文件「整型与枚举底层类型」与标识 `bg-comment-cases-v1` 的知识文件「整型转换注释」执行：理由记录在知识文件，注释不复述。仅当该处代码的主题就是类型或性能承载（NEON/SIMD、宽化窄化、位布局）时，类型说明才是正文语义，可以写。
- **写给作者的组织自述**：「全仓只在这里定义一次」类说明回答「维护者应在哪里定义」，不回答「读者应如何理解这行代码」，不进注释；单一出处等工程约束放知识文件或 Quarto 正文。

两类禁令都不影响契约注释：前置条件、异常与失败后动作（如「调用方应先用 IsValid 排除越界；非法坐标抛 std::out_of_range」）是读者正确使用 API 的必要信息，照常保留。正反对照见标识 `bg-comment-cases-v1` 的知识文件「类型选型旁白对照」。

## 领域函数与成员注释

领域 API 注释写**结果与约束**，不写抽象动作词。概述与能力行不用压缩式黑话（「向空格落子」「查询满盘」），用与函数名对应的平实说法（「放置棋子」「检查棋盘是否已满」——用户定案）。**函数概述一律以动词开头，且动词与函数名前缀硬对齐**（用户定案，覆盖旧「查询型成员概述取短结果名词句」）：读者扫注释时要一眼看出这是获取、检查还是受理动作。反面例：`棋盘是否已无空格。` 是名词短语，改写为动词陈述句。

**前缀动词表（声明 `///` 概述首词）：**

| 前缀 | 概述动词 | 例 |
| --- | --- | --- |
| `Get*` | **获取** | `/// 获取当前落子玩家。` |
| `Set*`（若出现） | **设置** | 不用纯名词句 |
| `Try*` | **尝试** | `/// 尝试执行一次落子。` |
| `Is*` / `Has*` | **检查** | `/// 检查棋盘上是否已形成该玩家的获胜线。` |
| `Place*` | **放置** | `/// 在指定坐标放置棋子。` |
| `To*` | **将…转换为…** | `/// 将二维坐标转换为一维索引。` |
| 构造函数 | **构造函数：** | `/// 构造函数：创建空棋盘，轮到 X 落子。` |
| 无前缀领域动词 | 与函数名动词一致 | `ResultAfterMove` → `/// 判定落子后的对局结果。` |

- **禁止**：纯名词短语概述（`/// 当前对局结果。`）；垫话长动宾（`/// 获取本局已执行的落子。` → 用「获取本局落子历史。」）；概述用「返回…」。
- 顺序说明等细节进细节槽，不塞进概述挤成名词句（如 `GetHistory` 的「按发生顺序排列」）。
- 动词规则**只约束函数**：类型、常量、枚举的概述仍用名词短语（`/// 对局玩家。`），不要求动词。
- `Get` 前缀不改（`History()`／`Result()` 式裸名词让调用点看不出只读访问；联网复核：Google 不强制 getter 前缀、Chromium 惯用 `Get` 前缀，本仓取显式前缀）。带副作用且可能被拒绝的受理动作取 `Try` 前缀、概述用「尝试…」（`Game::Place` 更名 `Game::TryPlace`，概述「尝试执行一次落子」，用户定案）。
- 概述禁止「接受」黑话：不写「尝试接受一次落子」「获取已接受的落子」这类以「接受」暗指写入成功的说法——读者看不出「接受」对应什么动作（用户定案，后续同类表达一律禁用）。替换：受理动作写「尝试…」；写入成功的结果写「落子已写入」或「已写入」，不写「已接受」；文件头说规则约束时直接写「只允许当前玩家落合法棋子」一类可观察事实，不用「接受/拒绝」当主语。

句式表：

| 场景 | 句式 | 禁止 |
| --- | --- | --- |
| 常量与类型声明（`kRows`、`CellState`、`CellPosition`、`Board`） | **`///` 单行概述**，类型直接写名词短语，不以「表示」开头；类与需补充说明的类型（如 `CellPosition`）用「概述 + 空 `///` + 细节」 | 用 `//` 写头文件声明注释；行尾标注漏 `<`；「表示…」开头的类型概述 |
| 构造函数 | **「构造函数：」开头**（如 `/// 构造函数：创建一个所有格子均为空的棋盘。`，用户定案） | 只写动作不标角色（读者扫注释时对不上这是构造） |
| 类型/领域换算（`PlayerToCellState`、`Board::ToFlatIndex`） | **由 A 得到 B**（`PlayerToCellState`）；`To` 前缀用**将 A 转换为 B**（`ToFlatIndex`）；需要时括号给一对例子 | 映射、翻译、棋子（指 `CellState`）、以排布术语当结果（「行优先下标」）、空话「作个…」 |
| 受理动作（`Game::TryPlace`、`Board::PlacePiece`） | **尝试…／放置…**，动词与函数名对应；拒绝条件写概述后正文段，执行结果写 `@returns` | 「尝试接受」一类暗指写入成功的黑话；「接受」「拒绝」当动词主语 |
| 读取（`GetCellState`、`Game::GetResult`、`GetHistory`） | **概述行以「获取」开头**（`/// 获取当前对局结果。`、`/// 获取本局落子历史。`、`/// 获取指定坐标处的棋盘格子状态。`）；带参数或失败边界时写 `@param`／`@throws`（如 `/// @throws std::out_of_range 坐标不在棋盘范围内。`），返回值非显然时用 `@returns`，纯复述概述则省略 | 纯名词短语概述（`/// 当前对局结果。`）；长动宾概述（「获取本局已执行的落子」）；只写「查询」不写结果；`Get` 概述用「返回」；裸英文参数名当主语；「必须合法」不点名 `IsValid` |
| 展示层转换（`CellSymbol` 等） | **转成…（展示用途）** 可保留「转成」 | 与领域换算混用「映射」 |

正反对照见标识 `bg-comment-cases-v1` 的知识文件「领域函数注释对照」。文件头与类上一行同样结果向：写「可读各格状态」等能力，不写含糊的「查询棋盘格子」。类概述的能力清单用短并列动宾（`/// 提供获取棋盘格子状态、放置棋子和检查棋盘是否已满的功能。`），不堆「提供获取……和获取……」的同义反复长串。指 `CellState` 时用术语「棋盘格子状态」，不用「棋子」。

存储成员注释**本体先行**：先写成员装的是什么（如 `// 棋盘格子的存储数组，按行依次存放。`），再补排布；不用「按行优先保存棋盘格子」这类以排布开头的句子——读者先要知道成员是什么，才轮到它怎么排。缩短（如为对齐列宽压缩注释）时先删排布、先后、写入动作这后半句，禁止删掉「它是什么」；判定口诀：删掉动词之后若不再剩下领域对象，这句就不能单独当成员或函数注释。声明注释已写顺序（如 `GetHistory` 细节写「先手的第一步在最前，最近一步在最后。」）不能成为成员注释不写本体的理由——英文成员名（`history_`）不算中文读者已经读到的本体，行尾仍要写「本局落子历史。」。

## 实现注释

`.cpp` 实现注释服务于「隔期回看能快速接上」。契约写在头文件 `///`，实现注释只补契约没写的实现要点（密度按用户定案高于 [Google Function Comments](https://google.github.io/styleguide/cppguide.html#Function_Comments) 的行尾基线）：

- 函数定义上一行**不写操作摘要**：契约已在头文件 `///`，摘要只是把它复述一遍（用户定案）。契约里没有的实现原因保留（如 `ReadOwnedLine` 上方「这一整行要留到比较结束，所以放进 `std::string`，不借用输入缓冲。」）；测试函数上一行的场景句保留，因为测试没有那份契约。
- 函数体内**关键步骤**（循环阶段、胜/平分支、历史写入、轮换条件）用行尾 `//`（与代码之间 2 空格）或步骤上方 `//` 注释；**拒绝 / `return false` 的原因**用行尾（如 PlacePiece 的 `return false;  // 目标格子已被占用，拒绝覆盖。`）。
- 关键步骤行尾注释提到某成员时，写出那个成员的领域名（如 `history_` 的写入写「成功写入才记录落子历史。」），不写「记录本步」这类只剩动作、没有对象的句子（本体先行的判定口诀见「领域函数与成员注释」）。
- 注释自己把对象写出：不写「该状态」「该玩家」「这个」，除非同一句里已经写出棋子、玩家或坐标。
- 不用「行：」「列：」这类词条冒号，写成完整的一句。
- 一句只说这一步判断什么；成功路径上只把代码翻译一遍的行尾注释删掉。
- 不用序数给已经出现过的类型或步骤重新编号。
- lambda 与局部助手只在名字和实参之外还有值得说的判断依据时，上一行写一句；名字已经把判断内容说清的不重复写（如 `HasPlayerLine` 里 `has_state`、`has_line` 两个 lambda，名字已说明各自判断什么，上一行不写注释，对角线前的空行就是分段）。禁止主体没有注释，却在旁边的循环上写一句对不上对象的话。
- **禁止**：隐喻或「第二道防线」类实现注；复述 `@param`；为凑密度给一行委托加废话。
- 三阶段（01/02/03）同一套注释文案；Quarto 围栏若摘实现，与源码逐字一致。
- 守卫/前置校验与主逻辑之间空一行分组（见标识 `bg-google-cpp-style-v1` 的知识文件「实现文件分组与垂直空白」）。
- 不复制 `@param` / `@returns` / `@throws` 标签到 `.cpp`；声明契约改动时同步核对定义处注释。`.cpp` 的**定义顺序随头文件声明序**（见标识 `bg-declaration-order-v1` 的知识文件）。正反对照见标识 `bg-comment-cases-v1` 的知识文件「实现注释对照」。

## 注释位置：上方 vs 行尾

位置由「注释在回答哪一类问题」决定，不是个人偏好。依据 Google C++（复杂代码块注释放代码之前、单行非显然语句用行尾且与代码隔 2 空格）、LLVM（块前上方、短注可尾）与 OpenCV/Doxygen（实体之前 `///`、成员之后 `//!<` 即本仓 `///<`；来源见文末）。

| 场景 | 位置 | 标记 |
| --- | --- | --- |
| 文件头横幅 | 独立多行 | `//===` + `//` |
| 头文件：常量/枚举类型/结构体/类/函数契约 | **上一行**（可多行骨架） | `///` |
| **枚举值** | **行尾（右侧）** | `///<`，列对齐，≤100 列 |
| **struct / class 公开或聚合数据字段** | **行尾（右侧）**；超宽走下方溢出回退 | `///<`（需文档时）；全量或全无 |
| **私有数据成员**（`board_`、`cells_`…） | **默认行尾** `//`；触发回退则整条改上一行 | 普通 `//`（不强制 `///<`） |
| `.cpp` 函数定义上一行 | **不写操作摘要** | —（契约在头文件 `///`；实现原因与关键步骤见「实现注释」） |
| `.cpp` 多语句步骤/技巧块 | **块上一行** | `//` |
| `.cpp` 单行非显然结果（尤其 `return false` / 拒绝） | **行尾**，代码后 2 空格 | `//` |
| 调用处 bool/nullptr 含义 | 实参旁 | `/*Name=*/`（本仓罕用） |
| 成功路径若注释只翻译语句 | **不写** | —（勿复述；见「实现注释」） |

**判定口诀：** 注释管整个函数或一整段逻辑 → 上方；管这一条语句的结果/拒绝原因 → 行尾；管枚举值/字段域名语义 → 行尾 `///<`。同一意图不得「有时上方、有时行尾」；超过约半行宽、或需两句 → 改上方。PlacePiece 判例：定义上一行不写操作顶注，`return false;  // 坐标无效或要写入的是空格，拒绝。` 留在行尾；把单句拒绝原因抬到 `if` 上方是禁止改法——条件已自明。

### 行尾超宽 / 声明过长：溢出回退

私有成员与 `///<` 字段若一律行尾，长类型（如 `std::array<CellState, …>`、`std::vector<Move>`）加注释易超 `ColumnLimit: 100`，或声明本身已被 clang-format 折行。规则：

1. **先按两个空格试行尾**：`代码  + 两个空格 + // 注释` 排成**单行**且总长 ≤100 → 用行尾。
2. **同组已有对齐列时再试对齐**：同一组声明已有行尾 `//` 排成列时，按对齐列再试一次。
3. **对齐超 100 先缩短**：缩短时先删排布、先后、写入动作，禁止为对齐删掉「它是什么」（`history_` 不能因 `GetHistory` 的声明注释已写顺序就缩成「按发生顺序存放。」——英文成员名不算中文读者已读到的本体，行尾留「本局落子历史。」）；删掉动词后不再剩领域对象的部分不能删，删掉就改变事实的才回退上方。
4. **缩短后仍超 100，或声明已折行**（类型与名不在同一物理行）→ **整条回退上方**：不把注释拆到续行右侧；改为成员上一行单独 `// …`（与代码邻接、不空行）。
5. **同一 class 内允许混用行尾与上方**，条件是每条都遵守 1–4；禁止「明明一行装得下却放上方」或「超宽仍挤行尾」。
6. 公开 `struct` 字段的 `///<` 同此规则；回退上方时仍用 `///` 单行概述贴在字段上（不用无 `<` 的行尾形式冒充上方）。

判例：`Board::cells_`（长 `std::array<…>`）走上方回退；`Game::history_` 行尾留「本局落子历史。」与同组成员对齐——本体先行的同时保持行尾对齐，是规则 3 的合法结果，不随意抬到上一行。

正反对照见标识 `bg-comment-cases-v1` 的知识文件「注释位置对照」。

## 文件头

每个源码文件的注释开头必须有一段用途块，让读者不读代码就知道文件是什么。不写版权、作者、日期（教学仓库）。结构：

1. 定宽横幅行；
2. 标题行：`文件名 - 一句话用途`；
3. 空注释行 + 1–3 行补充说明（短文件可省略）；
4. 收尾定宽横幅行；
5. 空 1 行后开始内容。

横幅模板（一律 100 列、纯 ASCII，与 `ColumnLimit: 100` 同一档；旧的「文件头横幅固定 80 列、不随列宽拉长」定案由本条覆盖）：

- C++ / JSONC：`//===` + 90 个 `-` + `===//`（整行正好 100 个字符）
- sh / CMake / YAML / TOML / 点文件：`#===` + 92 个 `-` + `===#`（整行正好 100 个字符）

规则：

- 横幅**单独成行、定宽 100 列、纯 ASCII**，标题不嵌在横幅行内——避免中日韩字符宽度不同导致的对齐破坏。写完用整行字符数核对，只在中间的 `-` 串上加减，首尾记号不动。
- Bash 的 shebang 永远是第一行，横幅从第二行开始。
- 短文件（约 ≤20 行）只写文件头，不加段横幅。
- Bash 长脚本在文件头横幅之后、可执行内容之前设「严格模式与工作目录」独立段横幅，收纳 `set` 与 `cd`/路径常量；`set`、`cd` 不散落在文件头与函数区之间。

## Bash 脚本次序

较长 Bash 脚本按 Google Shell Style Guide 组织次序：`set`（严格模式）→ `readonly` 常量 → 全部函数聚在一起 → `main` 定义 → 文件末行 `main "$@"`。函数之间不夹可执行代码；有多个函数时必须有 `main`。步骤「1. 配置」等运行期输出由 `main` 内的 `header` 调用承担，不再各自占段横幅。

## 段落分隔

文件较长（约 >20 行）且含多个职责块时，用段横幅分隔：

```text
<空 1 行>
<横幅行>
<标题行>
<横幅行>
<空 1 行>
<段落内容>
```

- 段标题一行写完，不嵌横幅；两段之间恰好一组横幅。
- 段标题是一个对象名，或一个动词加一个宾语。不加冒号后面接的步骤链，不用「先…再…」，不用「并」把两个动作串进标题，不把文件名写进段标题。步骤导航由运行期输出（如 Bash 的 `header`）承担，段标题不重述步骤。
- 段落内的子分组不需要横幅，用普通单行注释即可。

## 单行注释

- C++ 用 `//`、Bash 用 `#`，注释符后空一格：`// 说明`、`# 说明`。
- 写意图和关键约束，不复述代码（"做什么"由代码自答）；规范说理按「注释不承载规范说理」外移，不进注释。
- 完整句子；遵守 100 列（与 `.clang-format` 的 `ColumnLimit: 100` 一致）；超长时折为多行连续注释，后续行与首行注释内容对齐或紧随注释符。

## 多行注释

- 一律写成**连续的单行注释行**，不用 `/* */` 或盒式框线。
- 库对外头文件里的**声明注释**一律用 `///` Doxygen：常量、枚举、结构体、类与函数契约同一层（用户定案：先函数契约迁移，同日扩到类型与常量声明；LLVM StringRef.h、GlobalValue.h 的公开声明用 `///`，OpenCV utility.hpp 同为 Doxygen 但用 `/** @brief */` 块与 `//!<` 行尾，标记不同、语义相同，链接见来源）；枚举值与字段的行尾标注用 `///<`（见「枚举与常量行尾注释」）；文件级说明用横幅头；`///` 不用于实现注释（调研结论：LLVM 编码标准与 RIOT 等项目以 `///` 作 Doxygen 标记、`//` 作普通注释，`\param` 与 `@param` 等价、取一种保持一致即可；Google C++ Style Guide 全文不出现 Doxygen，本条不是对齐 Google 的结果）。

### 声明注释块骨架

声明注释统一按「概述 → 恰好一行空 `///` → 可选细节 → 恰好一行空 `///` → 标签」的骨架写，空行只出现在两个固定槽位：

```cpp
/// <概述：一句完结。>
///                                    // 槽 1：有后续内容时必有
/// <可选细节：连续多行 ///，中间不空行。>
///                                    // 槽 2：有细节且有 @ 块时才有
/// @param name <角色或约束，不复述类型名。>
/// @param[out] row <仅出参使用 [out]。>
/// @returns <仅当返回语义非显然；否则整行省略。>
/// @throws std::out_of_range <触发条件。>
```

- **槽 1**：概述之后、细节或首个 `@` 之前，恰好一行空 `///`。
- **槽 2**：仅当「有细节正文且后面有 `@` 块」时，在细节与 `@` 之间放一行空 `///`。
- **一段细节** = 槽 1 之后、槽 2（或首个 `@`）之前的连续 `///` 行；行数不限（100 列折行会变多行），逻辑上是一段。
- **禁止第三道空行**：不得再插入空 `///` 把细节拆成两段（旧 `Board`/`Game` 类「能力 / 尺寸」两道空行即违规）。
- 无细节、只有标签：概述 → 槽 1 → 直接 `@param`…（无槽 2）。
- 有细节、无标签（纯类型说明）：概述 → 槽 1 → 细节结束（无槽 2）。

### 类型 / 类注释

- 常量、枚举、结构体、类的概述独占第一行，类型直接写名词短语，不以「表示」开头（用户定案）。结构体等需补充说明的类型写「概述 + 槽 1 + 一段细节」：

```cpp
/// 棋盘格子的行列坐标。
///
/// 行和列从 0 开始；默认构造为 (0, 0)。
struct CellPosition { ... };
```

- **类细节最多一段（覆盖旧「三段式」定案）**：本体句后只允许**一段**细节，能力与结构约束合并进这一段，不再用第二道空行拆开：

```cpp
/// 井字棋的棋盘。
///
/// 固定 3 行 3 列；提供读取棋盘格子状态、放置棋子和检查棋盘是否已满的功能。
class Board { ... };
```

### 标签规则

- **标签顺序锁死**：细节正文 → `@param`（多行紧贴）→ `@returns` → `@throws`；`@` 标签彼此不空行。
- **`@param` 全有或全无**：要么覆盖全部参数、要么全不写；普通入参不写 `[in]`，仅出参/入出参写 `@param[out]` / `@param[in,out]`。描述写角色或约束，不复述类型名。
- **`@returns` 省略规则**：`void` 不写；非 `void` 仅当返回语义非显然（多分支、枚举码、成败）时写；若只会复述概述（如 `GetCellState` 的「该坐标处的棋盘格子状态」）则省略，保留 `@param`/`@throws`。谓词写成立条件（如「坐标在棋盘内。」），不写「返回 true，否则返回 false」。
- **`@throws`**：写 `@throws <异常类型> <何时抛>`；本仓继续用 `std::out_of_range`。
- **折行**：同一 `@` 条目续行缩进对齐描述首字；禁止在谓词「返回」中硬断。
- 正文点名参数直接写参数名（如「`position` 须先经 `IsValidPosition`」），禁止第三套标记 `@p` / `\arg`。
- **禁用标签**：`@brief` / `\brief`（首句即摘要，加了是视觉噪音）、`@sa` / `@note` / `@warning` / `@code` / `@pre` / `@post` / `@retval` / `@tparam` / `@file` / `@defgroup` / `@ingroup` / `@todo`。
- **Google 内容维度按需触发**：输入输出、空指针、所有权、重入/同步、性能敏感点。本仓当前值类型 API 无裸拥有权指针时不写这些；一旦出现可空指针、所有权转移或线程假设，写进细节正文一句中文，不新增 `@ownership` 一类标签。

### private 声明

头文件里出现的 private 成员/辅助函数：有签名外约束仍用 `///` + 标签（如 `ToFlatIndex`）；平凡数据成员用 `//` 邻接注释（如 `cells_`）。不把 private 契约挪到 `.cpp`，保持「声明即契约」的教学闭环。

### 描述性语气

注释概述用第三人称陈述（对齐 Google descriptive mood，如「把棋盘转成文本」「检查坐标是否在棋盘内」），不用祈使句（不写「打开文件。」）。

### 展开规则

- 参数、返回值或异常带函数名与类型签名**之外**的约束（前置条件、失败行为、异常、取值限制）时，按骨架写槽 1（+槽 2），再逐项 `@param`、`@returns`、`@throws`（如 `Board::GetCellState`、`Board::PlacePiece`、`Game::TryPlace`）。
- 无额外约束的简单函数只留单行 `///` 概述（如 `Board::IsFull`、`Game::GetCurrentPlayer`），禁止用 @ 标签复述函数名与类型签名。
- 失败行为等约束写在细节段，不塞进单条 `@returns`（如 `PlacePiece` 的「坐标无效、要写入的是空格或目标棋盘格子已有棋子时放置失败，棋盘保持不变。」）。
- Bash 函数不使用 `Arguments:` / `Outputs:` / `Returns:` 清单。不直观时用 1–2 行中文写出关键约束；参数含义从名字和函数体看不出来时，写进同一段话，不另起清单。

## TODO

未完成或临时够用的实现必须用 TODO 标注，禁止只写「见后续章」一类普通注释——后者无法用检索保证不遗漏。

TODO 与 `@` 标签分属两条格式轨：`@*` 只服务 API 契约（见「多行注释」），`TODO:` 只服务未完成工作；禁止 `/// @todo`。格式只保留 Google Hyphen（[Google TODO Comments](https://google.github.io/styleguide/cppguide.html#TODO_Comments) 与 `google-readability-todo` 一致）：

```cpp
// TODO: <参考> - <要做什么>
```

1. **参考**：优先 issue / bug（如 `b/12345`、GitHub issue URL）；本仓教学阶段尚无 issue 时，用将落地的阶段目录名或章节 slug（如 `01-cli-game`），不要只写人名。
2. **描述**：写清「现在缺什么、完成后应变成什么」，中文完整句、句号结尾。
3. 旧式 `TODO(参考): …`（Parentheses）降为「历史可识别、新码不写」；sh / YAML / CMake 用 `# TODO: ...`。

```cpp
// TODO: 01-cli-game - 从 cells_ 判断胜负或平局。
// 当前总是返回 kInProgress。
GameResult Game::GetResult() const {
  static_cast<void>(cells_);
  return GameResult::kInProgress;
}
```

TODO 表示临时方案；补全实现后删除该 TODO。可用 `rg TODO` / IDE TODO 视图做收口检查。未完成只认 `TODO:`，禁止用 `FIXME` / `HACK` / `XXX` / `NOTE:` 当检索标记；永久注意写细节正文或 Quarto。

## Python

- 调用者文档用 PEP 257 docstring（模块、类、公共函数）：单行 docstring 用 `"""一句话"""`；多行时首行为摘要、空 1 行、再写详情，收尾 `"""` 独占一行。docstring 回答「调用者怎么用」，性质接近 C++ 的 `///` 契约，因此文件头不另套横幅，避免同一模块出现两套文件头。
- 块注释用 `#`，粒度与键值配置的「一组一行」相同：一条注释只讲紧下面的一条语句或一组键；每行 `#` 前缀并与代码同级缩进；行内 `#` 注释与代码至少隔两个空格。
- 公共接口文档用 docstring，不用 `#` 注释。

## 空行总则

- 文件头横幅块之后空 1 行。
- 段横幅块之前空 1 行、之后空 1 行。
- 普通注释与被注释的代码之间不空行；逻辑上独立的代码块之间空 1 行。
- `.cpp` 函数**定义**之间空 1 行。
- `.cpp` 函数体内一段做一件事：同一段里性质相同的语句贴紧，中间不空行；换了一种检查或换了一步职责，段与段之间恰好空一行。函数首尾不空行，不连空两行。四家依据与判例见标识 `bg-google-cpp-style-v1` 的知识文件「实现文件分组与垂直空白」。

### 类声明垂直空白（源码与 Quarto 围栏同规）

| 位置 | 空行 |
| --- | --- |
| `public:` / `private:` 关键字后 | **不**空行（Google Class Format） |
| 连续**成员函数**声明之间（含构造与下一方法、带 `@` 多行注释块与下一方法） | **恰好空 1 行** |
| 同一 access 段内，最后一个函数与第一组**数据成员**之间 | **空 1 行** |
| 连续**数据成员**之间 | **不**空行（一组贴紧；注释按「注释位置」行尾或上方） |
| `public` 段与 `private` 段之间 | `private:` 前空 1 行（Google；首个 access 除外） |
| 函数体开头/结尾 | 不空行；体内仅逻辑块之间空 1 行 |

以 `[[` 开头的属性与声明同一行，缩进与普通成员相同，不单独占访问说明符那一列，其后也不插空行。

Quarto 摘录 class / 多函数片段时**保留**源码中函数之间的空行，禁止为省行数坍缩；省略部分成员时，被保留的相邻函数之间仍空 1 行。与「逐字摘录」冲突时以源码空白为准：教学缩略可删成员，不可删「函数间距」惯例。案例见标识 `bg-comment-cases-v1`，围栏规则见标识 `bg-qmd-element-cases-v1`。

### 类内属性与访问说明符空白

上一段的属性行空白由 `.clang-format` 锁定：`AccessModifierOffset: -1` 配 `IndentWidth: 2`，访问说明符缩进 1 格、成员缩进 2 格；`EmptyLineAfterAccessModifier: Never` 删去访问说明符后的空行；`BreakAfterAttributes: Never` 阻止在属性组后断行。`EmptyLineBeforeAccessModifier` 保持 Google 默认 `LogicalBlock`，`private:` 前的 1 行空行不由配置显式管理。版本要求与官方依据见标识 `bg-google-cpp-style-v1` 的知识文件「类内属性与访问说明符空白」；编辑器侧 clangd 的版本要求见标识 `bg-development-environment-v1` 的知识文件「编辑器」。

## 注释语言与内容风格

- **语言跟随读者**：OpenHarmony 面向国际社区选择英文注释，说明注释语言取决于目标读者；本仓库的目标读者是中文初学者，注释正文一律使用**简洁、明了、新人易懂的中文**。
- **中文术语以 `bg-cpp-chinese-terms-v1` 为准**：访问控制、类与成员、声明定义、类型对象等 C++ 概念点名时按全表用词；读者侧禁用行见 `bg-terminology-v1`。本文件只写注释形态规则，不另立术语表。
- **专业名词保留英文**：工具名（CMake、Ninja、Clang、clangd、CTest、g++、VS Code、GitHub Actions）、命令与关键字（`target_compile_features`、`PRIVATE`）和无通行中文译名的技术术语（target、stdout/stderr、TTY 等）直接写英文原文；有通行中文说法的普通词用中文，不刻意夹杂英文。
- **中文语法与标点**：
 - 完整句子要有主谓结构，一句话说一件事，避免多重复句堆叠和翻译腔。
 - 中文句子用全角标点（，。：""）；普通邻接注释默认使用简洁完整句，并以句号结尾；仅枚举行尾的单词式说明可省略句号。
 - 中文与英文单词、数字之间加一个半角空格（如"使用 CMake 配置"），便于阅读和检索。
- **内容取舍**（Google、Linux 内核、OpenHarmony 共识）：讲 WHAT 和 WHY，不讲 HOW；不重复代码能自表达的信息；从读者的角度按需注释，不写空有格式的注释；改代码时同步维护注释；不用的代码段直接删除，不注释掉。

## 键值配置

键值配置文件指 `.clang-format`、`.clang-tidy`、`.clangd`、`.gitignore`、`.gitattributes`、`.editorconfig` 和 `config.toml`。它们与源码/CMake/sh 共用文件头横幅模板（100 列），组与组之间空一行，但**不用段横幅**；组注释按 100 列折行。一律不写行尾注释——即使 TOML 允许行尾 `#` 也不写，避免和 Git 的忽略规则打架（gitignore 里不在行首的 `#` 不是注释）。例外只有两条：gitignore 的 `#` 必须整行行首才算注释；clang-tidy 的 `#` 不能折进 `Checks: >` 折叠字符串，否则变成检查名。

注释粒度按文件分开：`.clang-format` 是一组键一行分组注释，`.clangd` 是键上一句覆盖整组值，`.clang-tidy` 是关闭项上方写原因，`.gitignore`、`.gitattributes`、`.editorconfig`、`config.toml` 是一组模式或一键一行。共同纪律：只标非自明项；紧贴被约束的键、模式或 list item；`#` 后一空格；完整中文短句，一句一个中心；专有名词保留英文；≤2 行。正反对照见标识 `bg-comment-cases-v1` 的知识文件「键值配置正反对照」。

### 禁止形态

- 文件顶部长篇政策块（Google 主标准、偏离白名单、`at()` 全局策略、知识库 id 指针）折成多行 `#`。
- 注释内出现 `bg-*` / `cpp-*` / `.agents/`，或「见知识库…」。
- 阶段副本残留模板元叙述（「两仓统一基准源」「把本文件复制…」「与 cpp-notes 保持一致」）。
- 一段注释同时覆盖多条 `Checks` 关闭项或多组 `CheckOptions`（违反「一注一句」）。

### 文件头

LLVM 定宽横幅 + 标题行「文件名 - 一句话用途」+ 收尾横幅；标题下**不再**跟补充政策段。三文件一律要横幅（不因篇幅短而省略）。

### .clang-format：一组键一行分组注释

- 一组相关键上方一行注释，形如「行宽：普通代码行限制为 100 列。」——冒号前点名这组键管什么，后面写取舍或结果；依据 [ClangFormat Style Options](https://clang.llvm.org/docs/ClangFormatStyleOptions.html)，注释贴在一组键上方，说明相对基础风格的取舍。
- 键值自明的组不再逐键注释；禁止分组注释下再堆政策折行。
- 阶段副本与模板保持同一外形；键值不变时注释不改。

### .clangd：键上一句覆盖整组值

- 注释贴在键上方，覆盖这一键的整组值，不在各个值上重复同一句（依据 [clangd FAQ](https://clangd.llvm.org/faq) 与 [clangd config 文档](https://clangd.llvm.org/config)）。
- `CompilationDatabase` 保留一句：构建后从 `build/compile_commands.json` 读取真实编译参数。
- `Add` 键上一句说明这是未生成编译数据库时的解析兜底，与目标的 C++ 标准、标准库和警告选项一致；其下的 `-std`、`-stdlib`、`-Wall`、`-Wextra`、`-Werror` 不再各写一行。
- 头文件搜索路径单独一句（如「未构建时的头文件搜索路径，相对本文件目录。」）——路径是阶段差异，各 `-I` 不再复述「未构建时」。
- `Diagnostics.ClangTidy.Add` 键上一句说明补上的检查与同目录 `.clang-tidy` 一致；检查名不逐条注释。
- `Suppress` 保留现有一句：只压制首次未构建时找不到头文件的噪音，构建后以编译数据库为准。
- 模板不写具体游戏路径，也不写「复制后按阶段增删」类元叙述；库头路径写成阶段会替换的 `-I` 示例，复制说明只留在 `cpp-development` 的 SKILL.md。

### .clang-tidy：关闭项上方写原因

- 继续用 YAML 列表，不用 `Checks: >` 折叠字符串：`.clang-tidy` 是 YAML，`#` 到行尾才是注释，折进折叠字符串的 `#` 会变成检查名（依据 [clang-tidy 文档](https://clang.llvm.org/extra/clang-tidy/)）；LLVM 仓库自己的 `.clang-tidy` 用折叠字符串，本仓不跟。
- 启用的 glob 与逐项列出的 google 检查上方一行分组注释；名字和理由分开（Chromium 把否决理由放在启用列表之后的注释块里）。
- 每个关闭项上方只写原因，不把检查名再写一遍——检查名已经在下一行。
- `CheckOptions` 开头一行说明类型用 CamelCase、变量和参数用 lower_case、常量与枚举子用 `k` 前缀；自明键不再逐条注释；仅对偏离直觉的项（如 `LocalConstantCase`）邻接一句偏离说明。
- 不全局关闭 `cppcoreguidelines-pro-bounds-constant-array-index`；边界与 `at()` / 局部 `NOLINT` 见标识 `bg-static-analysis-boundaries-v1` 的知识文件。

### 与 CMake / sh 的异同

`.sh` 与 `CMakeLists.txt` 是过程脚本，共用同一套：文件头横幅加上，文件较长时用段横幅划分职责块，块内仍是「一条语句正上方一行」；Bash 函数不写 `Arguments:` / `Outputs:` 清单。键值配置文件无段横幅，只用文件头 + 单行分组/邻接。说理进 `.agents/knowledge/`，读者工程句进 Quarto，注释只答「这项约束什么」。

## 长注释与文档分层

Linux 内核警告"过度注释有危险"（"there is also a danger of over-commenting"），长篇 API 与设计说明走独立的 kernel-doc 与 Documentation/ 体系，不堆在代码里。本仓库对应分层：`.agents/knowledge/` 放完整论证与外部依据（Agent 按主题检索），Quarto content 放面向读者的讲解。

- **上限**：紧跟代码的说明注释不超过 **2 行**；文件头横幅和函数结构化头注释等已有格式规定的块不受此限。
- **超限处理与分层**：注释只留 1–2 行结论和关键动作（如出错时 `rm -rf build`）；完整论证、方案对比和外部链接移入 `.agents/knowledge/`，面向读者的讲解放 Quarto 对应章节；注释不加指向知识库的指针，三处不得全文重复。
- **内部路径禁令**：`games/**` 与 `content/**` 下的任何文件（代码、脚本、配置注释、qmd 正文）不得出现 `.agents/` 路径引用。games 源码会被 Quarto include 展示给读者，content 是读者文档，内部知识路径混入会混淆读者与作者视角；Agent 所需论证一律回本知识库按主题检索，不通过代码注释跳转。
- **精简手法**：一句话说一件事；"为什么不用某方案"的整段对比论证移入知识文件，注释不展开。

## 来源

- [LLVM Coding Standards](https://llvm.org/docs/CodingStandards.html)——横幅分段、`\file` 文件级注释、`///` 文档注释与 `//` 普通注释之分；首句即 abstract、后续信息用空行隔开，显式 `\brief` 是噪音；[Comment Formatting](https://llvm.org/docs/CodingStandards.html#comment-formatting) 不强制「一律上方或一律行尾」，块前上方、短注可尾。
- [Google C++ Style Guide · Implementation Comments](https://google.github.io/styleguide/cppguide.html#Implementation_Comments)——复杂/重要代码块注释放**代码之前**；单行非显然语句用**行尾**注释并与代码隔 **2 个空格**，多行行尾可列对齐。
- [Doxygen 手册](https://doxygen.nl/manual/docblocks.html)——`///`/`//!` 特殊注释与 `///<` 行尾成员文档语法；空行结束 brief；多行 `///` 默认整体不当作 brief。
- [Doxygen commands](https://www.doxygen.nl/manual/commands.html)——`@return`/`@returns`、`@throw`/`@throws`/`@exception` 同义，本仓取陈述性复数 `@returns` / `@throws`。
- [OpenCV documenting tutorial](https://docs.opencv.org/5.0/tutorials/introduction/documenting_opencv/documentation_tutorial.html)——`@` 前缀习惯、参数要么全写要么全不写、常用 `@returns`。
- Pigweed / LSST / Drake 实践——统一 `@` 前缀、倾向 `@returns` / `@throws`、方向标注 `[in]`/`[out]` 可选。
- 判例头文件：[LLVM StringRef.h](https://github.com/llvm/llvm-project/blob/main/llvm/include/llvm/ADT/StringRef.h)、[GlobalValue.h](https://github.com/llvm/llvm-project/blob/main/llvm/include/llvm/IR/GlobalValue.h)——公开声明用 `///`（LLVM 编码标准：普通注释 `//`、Doxygen 注释 `///`）；[OpenCV utility.hpp](https://github.com/opencv/opencv/blob/4.x/modules/core/include/opencv2/core/utility.hpp)——Doxygen 用 `/** @brief */` 块与枚举成员 `//!<` 行尾（与 `///<` 语义等价）。
- [Google C++ Style Guide](https://google.github.io/styleguide/cppguide.html)——文件头描述内容、`//` 优先、TODO 格式、注释写意图、注释语法不要求 Doxygen。
- [Google Shell Style Guide](https://google.github.io/styleguide/shellguide.html)——文件头、函数结构化注释、"不要事事注释"。
- [Linux kernel coding style](https://docs.kernel.org/process/coding-style.html)——第 8 章"注释讲 WHAT 和 WHY、不放函数体内"，多行盒式注释仅作对比不采用。
- [OpenHarmony C++ 语言编程规范](https://gitee.com/openharmony/docs/blob/master/zh-cn/contribute/OpenHarmony-cpp-coding-style-guide.md)——注释"简洁、明了、无二义性"、从读者角度按需注释、注释与代码同步维护；其"注释语言跟随读者"的取舍是本仓库选中文注释的参照。
- [Learn C++ 1.2 Comments](https://www.learncpp.com/cpp-tutorial/comments/)——函数上方写它要完成什么、函数内部写怎么完成、单条语句写为什么；把语句再翻译一遍的行尾注释是坏注释（「实现注释」与「注释位置」的分层依据）。
- [Learn C++ 1.3 Introduction to Objects and Variables](https://www.learncpp.com/cpp-tutorial/introduction-to-objects-and-variables/)——一个变量一行，行尾注释写这个变量作什么用（成员行尾注释写本体的依据）。
- [C++ Primer 5e §1.3 A Word about Comments](https://cpp-primer.pages.dev/book/013-1.3._a_word_about_comments)——注释用来概括算法、指出变量的用途，或说明看不懂的片段；注释不改变行为，只帮助人读。
- [cppreference Manual of style](https://en.cppreference.com/w/Help:Manual_of_style)——描述的第一句必须概括该实体的行为；类页先说这个类型是什么；容器条目用名词短语（如 vector 的 "resizable contiguous array"），不写「按 push_back 的次序存放」（「本体先行」的判据来源）。
- [Google C++ 风格指南中文版 §8 注释](https://zh-google-styleguide.readthedocs.io/en/latest/google-cpp-styleguide/comments.html)——类数据成员写用途，类型和名字已说清就不必再注，特殊值（如 `-1`）的含义必须写；英文原文示例 "Keeps the total number of entries" 先写用途、再写特殊含义。
- 欧长坤《现代 C++ 教程》[附录 2](https://github.com/changkun/modern-cpp-tutorial/blob/master/book/zh-cn/appendix2.md)——注释解释「为什么」，代码本身已经说明「做了什么」；函数保持短小、一件事一件函数。
- [ClangFormat Style Options](https://clang.llvm.org/docs/ClangFormatStyleOptions.html)——多语言示例：注释贴在一组键上方，说明相对基础风格的取舍。
- [clangd FAQ](https://clangd.llvm.org/faq) 与 [clangd config](https://clangd.llvm.org/config)——`.clangd` 的注释贴在键上、覆盖该键整组值的依据。
- [clang-tidy 文档](https://clang.llvm.org/extra/clang-tidy/)——`.clang-tidy` 是 YAML，`#` 到行尾才是注释；折进 `Checks: >` 的 `#` 会变成检查名。
- Chromium 与 LLVM 仓库的配置文件——Chromium 把否决理由放在启用列表之后的注释块里，名字和理由分开；LLVM 自己的 `.clang-tidy` 用折叠字符串，本仓不跟。
- [PEP 8](https://peps.python.org/pep-0008/)、[PEP 257](https://peps.python.org/pep-0257/)——Python 注释与 docstring。

程序运行时向终端打印内容（阶段标题、进度、错误、日志）的展示形式不属于注释范畴，另见 标识 `bg-terminal-output-style-v1` 的知识文件。
