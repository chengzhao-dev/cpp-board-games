# 工程八步流程与 STAR 故事线

本文件是「八步开发流程 + STAR 成果故事线」的唯一权威，供 Agent 规划游戏章节叙事、分配章内职责和执行开发流程使用。面向读者的摘要只写在各游戏的首章与末章，本文件不复制成读者内容。

## 八步开发流程

| 步 | 谁做 | 输入 | 输出 |
| --- | --- | --- | --- |
| ① 短需求 | 人 | 想解决的问题 | 100–300 字需求短文：输入、输出、模块划分 |
| ② 设计目录 | 人 | 需求短文 | 目录树与文件落点（组件布局依据见标识 `bg-staged-game-layout-v1` 的知识文件） |
| ③ 划分职责 | 人 | 目录树 | 模块职责与模块间数据流：谁持有状态、谁提交动作、边界在哪 |
| ④ 生成实现 | AI | ②③ 固定的边界 | 模块内部代码 |
| ⑤ 人读代码 | 人 | AI 产出 | 修掉不合理处后的代码；不合理即改，不为省事迁就 |
| ⑥ 单元测试 | 人 + AI | 模块接口 | 覆盖关键行为的测试并注册到 CTest |
| ⑦ 运行调试 | 人 | 可执行产物 | 报错记录：症状 → 定位 → 修复 → 验证 |
| ⑧ README | 人 + AI | 稳定的工程 | 编译、依赖、运行、测试四项要点 |

## STAR 四段模板

每个游戏一套 STAR，用读者的语言写，不复述流程名词：

- **S（问题）**：这个游戏解决什么学习与工程问题。
- **T（任务）**：要实现哪些模块、选了哪些工具、为什么。选型叙述只写真实已选工具（C++20、CMake、Ninja、Clang、CTest、WSL）；示例性第三方库用「若引入则…」或进延后项，不假写进当前游戏。
- **A（行动）**：架构划分、代表性踩坑与修复；坑的完整排查写在中间章常见错误，此处只作摘要并链接出处。
- **R（成果）**：当前可观察成果（可构建、测试数、可运行行为）、已知可优化点与延后项。

延后项不设集中页。井字棋只在第五章末留一句：新的对手产生 `Move`，调用同一个 `Place`。`06-opponent.qmd`、`07-search.qmd` 与 `08-replay.qmd` 的职责写在标识 `bg-roadmap-v1` 的「已设计、未实现」，对应目录可构建之前不注册进读者书。

## 与仓库目录的映射

| 故事线元素 | 落点 |
| --- | --- |
| ① 短需求 | 第一章 `content/tictactoe/01-rules.qmd`：对局输入、输出与结束条件 |
| ② 目录 | 第二章 `content/tictactoe/02-project-layout.qmd`：`01-cli-game` 的目录、文件职责与依赖方向 |
| ④⑤⑥ 实现与测试 | 第三章 `03-board.qmd`、第四章 `04-game.qmd`，验收动作在终端章展开 |
| ⑦ 报错记录 | 第二章到第五章的「常见错误」；不面向读者且排查价值高的进 `.agents/incidents/` |
| ⑧ 运行与成果 | 第五章 `05-terminal-play.qmd`：终端输入输出、配置、编译、测试与运行 |
| 可运行证据 | `games/tictactoe/01-cli-game/build-and-run.sh` 与 CTest |

后续新游戏（四子棋等）复用同一模板：各自首章写本游戏 S/T，末章写 A/R，中间章常见错误记本游戏坑。

## 硬约束

1. 需求短文（①）由人起草；AI 只能基于已确认的短文展开，不得代写需求再自行实现。
2. AI 不跳过 ①–③ 直接写模块内部实现；②③ 未固定时，先补边界再写代码。
3. ⑦ 的报错记录进章内「常见错误」或 `incidents/`，不进 01 与末章主叙事；末章 A 只作摘要并链接出处。
4. STAR 的 T 不预写未选型的工具；中间章不复述整套八步或完整 STAR。
